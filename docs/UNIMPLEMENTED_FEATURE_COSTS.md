# Estimated Cost of Unimplemented Features

Snapshot: **2026-11-01**. This document estimates the engineering and runtime footprint of the features marked **TODO**, **MAYBE**, or **NOT PLANNED**, plus meaningful extensions to partially implemented features, in [TELEGRAM_FEATURE_MATRIX.md](TELEGRAM_FEATURE_MATRIX.md).

These are planning estimates, not commitments or measured build results. They assume the existing Rust/Tokio/ratatui/TDLib architecture, a Linux TUI, and no changes to Telegram's service. Estimates are for a usable, permission-aware workflow with basic automated tests, not full official-client parity. TDLib support and the `tdlib-rs` bindings must be checked for each operation before implementation; unsupported bindings can add substantial work.

## How to read the estimates

| Size | Approximate new/changed Rust code | Typical effort | Meaning |
|---|---:|---:|---|
| XS | 50–200 LOC | 0.5–2 engineer-days | Small existing workflow extension. |
| S | 200–600 LOC | 2–5 engineer-days | One focused action or simple panel with tests. |
| M | 600–1,500 LOC | 1–3 engineer-weeks | Several UI states plus client/store mapping and failure handling. |
| L | 1,500–4,000 LOC | 3–8 engineer-weeks | Multiple workflows, complex async state, broad test surface. |
| XL | 4,000+ LOC | 2+ engineer-months | New platform/runtime subsystem or external ecosystem integration. |

Code ranges are incremental, rounded order-of-magnitude estimates. Shared infrastructure can reduce the sum when features are implemented together; unsupported TDLib APIs, compatibility work, accessibility, and robust edge handling can increase it.

Runtime footprint is relative to current `tgt`, excluding the already-linked TDLib native library. “App size” means expected Rust binary/dependency growth, not the user's TDLib database or downloaded media. New dependencies should be optional Cargo features when not needed by the core client, consistent with `docs/ARCHITECTURE.md`.

## Dependencies and build-size notes

- The current workspace already includes `tdlib-rs`, Tokio, ratatui, image support (optional behind `media-preview`), `arboard`, and desktop notification support (optional behind `notifications`). Many straightforward Telegram API workflows should not need a new Rust crate if `tdlib-rs` exposes the required types and methods.
- The native TDLib library is a major distribution/build dependency already. The estimates above describe incremental Rust-side growth and do not include the size of TDLib itself.
- New media decoding, browser/WebView, real-time audio/video, or OS-specific APIs can dominate binary size and build complexity. Gate such capabilities behind optional Cargo features and assess system-library availability early.
- Runtime impact is usually low for forms and request/response features. The main cost drivers are multiple TDLib clients, large result/member lists, concurrent transfers, image/GIF decoding, persistent queues, and real-time media.
- Before committing to any MAYBE or NOT PLANNED feature, verify the exact TDLib API and generated binding availability, supported Linux environments, and how the workflow fits terminal interaction.
